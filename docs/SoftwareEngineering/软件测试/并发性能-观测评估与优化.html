并发性能：观测、评估、优化

这篇笔记把"并发性能"拆成三件互相依赖的事：先观测、再评估、最后优化。顺序颠倒就会做无用功——没有观测的优化是猜，没有 SLO 的压测是数字游戏。

一、三件事的关系​

阶段目的产物
观测把"看不见"变成"看得见"指标 dashboard、慢查询清单、池状态曲线
评估用可控负载逼出瓶颈压测报告、达标/不达标的 SLO 清单
优化按数据动手代码改动、参数调整、扩容方案

顺序不能颠倒。先扩容再观测、先调参再压测，常见且常错。

二、先定 SLO，再谈数字​

压测前必须先回答："多快算够快？多稳算够稳？"否则压出来的数字无从判断好坏。

一条 SLO 的典型形式：

30 天内，登录接口 P95 延迟不超过 300ms 的请求占比 ≥ 99%

压测脚本的 threshold 应该和这条 SLO 一一对应——脚本本身就是 SLO 的可执行版本。

起步参考（按场景分桶，不要"平均延迟一刀切"）：

接口类型P95 延迟 SLO错误率 SLO
鉴权 / token 刷新< 300ms< 0.1%
列表 / 详情（DB read）< 500ms< 0.1%
长链路任务（LLM / 沙箱）首响应 < 3s< 1%
写事务 / 跨服务< 1s< 0.1%
可用性月 ≥ 99.5%—

SLO 的完整方法论——SLI / SLO / SLA 三者差别、错误预算、Burn Rate 告警、月度复盘——拆到了独立笔记：

👉 SLI / SLO / SLA：服务等级目标

下面默认读者已经理解 SLO 概念，专注压测本身。

三、观测层：要测什么、用什么​

3.1 数据库​

PostgreSQL 是最常见的瓶颈，看四类指标：

指标来源看什么
连接状态pg_stat_activitystate 分布：active / idle / idle in transaction / waiting
慢查询pg_stat_statements（扩展）total_exec_time 倒序 top 20
锁等待pg_locks join pg_stat_activity阻塞链
事务速率pg_stat_databasexact_commit、blks_hit/read 比率

idle in transaction 长期非零通常意味着连接泄漏——不是缺连接，是有事务没关。设 idle_in_transaction_session_timeout=60s 当兜底，但要把它当成 canary，不是常态。

3.2 应用连接池​

应用层池可见性是最容易被忽略的一环。SQLAlchemy 提供 pool 事件：

from sqlalchemy import event

@event.listens_for(engine.sync_engine, "checkout")
def on_checkout(dbapi_conn, conn_record, conn_proxy):
    pool_metrics.checkout_total.inc()

@event.listens_for(engine.sync_engine, "checkin")
def on_checkin(dbapi_conn, conn_record):
    pool_metrics.checkin_total.inc()

把 pool.status() 暴露成 /internal/metrics/db，永久能查"现在池里几条、checked-out 几条、等多久"。这是事后定位泄漏的最有力证据。

3.3 请求延迟与并发​

按四个维度分桶记录，不要合并平均：

  • 路由分桶：不同 endpoint 的瓶颈完全不同
  • 延迟分位：P50 / P95 / P99；只看均值会被异常值掩盖
  • 并发请求数（in-flight）：和延迟一起看才能区分"慢"和"挤"
  • 错误码：4xx 是客户端问题，5xx 是服务端

Python 后端常见组合：structlog 写日志、OpenTelemetry 出 trace、prometheus_client 暴露 metrics、Sentry 兜住异常。

3.4 Celery 与 Redis​

指标工具 / 命令含义
队列深度redis-cli LLEN celery任务积压量
Worker 活跃celery inspect active 或 Flower当前在跑的任务
任务延迟 P95自打点或 Flower入队到完成的时长
重试率自打点retry / total
Redis 连接数redis-cli info clients防连接泄漏
缓存命中率info stats 的 hits/misses缓存有效性

3.5 外部依赖​

  • 第三方 API：调用次数、P95、失败率，分服务商分桶
  • 沙箱 / 容器池：池容量、申请等待时长、回收失败次数
  • 跨内部服务：链路追踪贯穿 trace_id

外部依赖的长尾通常吃掉系统大半的 P99 预算。

四、评估层：怎么压​

4.1 工具：为什么选 k6​

k6 是 Grafana Labs 开源的压测工具，单二进制、脚本写 JS、threshold 内置、Prometheus 友好。

横向对比：

工具语言适用场景短板
k6JS 脚本 + Go 引擎多步骤场景、CI 门禁、容器化压测JS 写复杂逻辑啰嗦
LocustPythonPython 团队、需要复杂业务逻辑需要单独 Python 环境，单机性能弱
JMeterJava + XML老牌、企业环境XML 难维护、上手重
wrk / vegetaC / Go单 URL 极致 RPS不支持多步骤、不带 token

多步骤场景（登录拿 token → 调业务接口）选 k6 或 Locust，不要选 wrk。

4.2 k6 最小骨架​

// login-then-invoke.js
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '30s', target: 10 },   // 30s 内爬到 10 并发
    { duration: '2m',  target: 10 },   // 维持 2 分钟
    { duration: '10s', target: 0 },    // 收尾
  ],
  thresholds: {
    http_req_duration: ['p(95)<300'],  // 把 SLO 写进代码
    http_req_failed:   ['rate<0.001'],
  },
};

export default function () {
  const login = http.post('http://localhost:8000/api/auth/login', {
    phone: '13800000000', code: '1234',
  });
  check(login, { 'login 200': r => r.status === 200 });
  const token = login.json('access_token');

  const res = http.get('http://localhost:8000/api/sessions', {
    headers: { Authorization: `Bearer ${token}` },
  });
  check(res, { 'list 200': r => r.status === 200 });
  sleep(1);
}

threshold 未达标时 k6 的 exit code 不为 0，可以直接接 CI 当性能回归门禁。压测脚本本身就是 SLO 的可执行文档。

4.3 测试形态：四种缺一不可​

形态形状目的时长
Baseline单并发找单请求理论最小延迟，作锚点1–2 分钟
Ramp-up阶梯 1→10→50→100找延迟拐点和容量上限10–20 分钟
Soak中等并发持久跑暴露泄漏（连接、内存、句柄）30 分钟 – 2 小时
Spike瞬间 10× 流量看降级 / 限流 / backpressure 是否生效5–10 分钟

Soak 测试最容易被省略，但它是连接泄漏类问题的唯一暴露途径。 短压测看起来稳，soak 跑 30 分钟连接数曲线开始爬，问题就显形了。

4.4 场景拆分​

不要混着压。把请求按"业务路径 + 资源画像"分类：

场景主要消耗压测时关注
鉴权CPU（JWT 签名）+ DB readRPS 上限、CPU 饱和点
列表 / 详情DB read + cache缓存命中率、慢 SQL
长链路任务LLM + 外部 IO + 长事务同时持有的长连接数
写事务DB write + 跨服务锁等待、分布式事务一致性

**RPS 是无状态短请求才有意义的指标。**长链路任务真正贵的是"同时持有多少长连接"，不是"每秒能起多少个"。

4.5 数据与环境​

  • 测试账号用真实 token，别用 /healthz 撑数据
  • 测试机和被测机分开，避免相互抢 CPU
  • 压测期间禁用对外隧道（ngrok 免费版有 RPS 限制，会污染结果）
  • 压测前快照一份 DB，压完恢复，避免数据污染

五、优化层：按 ROI 排序，不要倒过来​

工程团队常见的错误顺序：先扩容、再调参、最后改代码。正确顺序反过来：

5.1 改代码（最便宜，常常最有效）​

  • 同步 IO 漏进 async 路径：requests.get 写在 async def 里、time.sleep 没换 asyncio.sleep、CPU 密集型操作没丢 run_in_executor。这是 async 框架最常见的退化。
  • N+1 查询：用 SQLAlchemy 的 selectinload / joinedload，一次查完。
  • 大对象序列化：响应里塞了用不到的字段，序列化吃 CPU。
  • 诊断手段：开 asyncio debug mode 跑一轮 soak，会直接报 "Executing took X ms"。

5.2 缓存策略​

  • 加 cache 容易，invalidation 难十倍——能用 TTL 不用 pub/sub。
  • 区分"热点静态数据"（用户配置、菜单）和"实时数据"（库存、余额），后者别盲目加 cache。
  • 看命中率，不要看缓存条目数。

5.3 池与并发参数（要有数据支撑）​

参数怎么定注意
pool_size压测峰值 checked-out 数 × 1.2没吃满之前不要动
max_overflowpool_size × 0.5突发用，长期靠它撑说明 pool_size 不够
pool_recycle略小于 PG 端 idle_in_transaction_session_timeout防 stale connection
pool_pre_pingTrue多花一次 ping，换稳定性

参数变成 env var，不要写死，否则环境间差异调不动。

5.4 横向扩进程​

  • uvicorn --workers N：N ≈ CPU 核数，但 N × pool_size 不能超过 PG max_connections。
  • celery --concurrency：IO-bound 用 gevent/eventlet 池可以开很高；CPU-bound 等于核数。
  • 进程数变了，DB 连接总数跟着变，重算 PG 容量。

5.5 中间件层（PgBouncer 等）​

PgBouncer 解决"应用进程数 × pool_size > PG max_connections"这一类问题，不解决应用层连接泄漏。上之前先问："我的问题是 PG 不够开，还是应用没关好？"答案是后者，加 PgBouncer 只会让泄漏潜伏更久。

引入 PgBouncer 的代价：

  • transaction 模式下 prepared statement / SET LOCAL 受限
  • asyncpg 需要 statement_cache_size=0
  • 多一层网络跳转、多一处可观测盲点

5.6 PG max_connections 上调​

最后手段。每个连接约 10MB 共享内存开销，盲目调大会让 PG OOM。调之前先看 pg_stat_activity 是不是真的连接用完，而不是死锁、长事务、磁盘 IO 拖死。

六、常见反模式​

想法反驳
"先把 pool_size 调大稳一点"池小是表象，泄漏是病因。调大只让泄漏潜伏更久、更难复现。
"上 PgBouncer 一劳永逸"它解决的不是你的问题，引入它本身有新坑。
"并发性能就是 RPS"RPS 是无状态短请求指标。长链路服务看"同时持有的连接数"。
"压 /healthz 5000 RPS 没问题就稳了"/healthz 不碰 DB、不走 auth，跟生产路径无关，结论无效。
"压一次就行"Soak 测试单独跑，短压测发现不了泄漏。
"先扩容看看效果"扩容掩盖问题。连接泄漏被扩容掩盖几个月，定位成本翻十倍。
"P95 < 300ms 就够了，P99 不重要"P99 是 1% 的用户体验。SaaS 千万 DAU 时 1% 是 10 万次卡顿。

七、工具速查​

用途工具备注
压测脚本k6单二进制、CI 友好
PG 连接观测pg_stat_activity、pg_stat_statements后者需要装扩展
链路追踪OpenTelemetry + Jaeger/Tempo找跨服务长尾
指标Prometheus + Grafana配合 Loki 看日志
异常Sentry兜底未捕获错误
Python 性能采样py-spy、asyncio debug mode找 event loop 阻塞
Celery 监控Flower任务级 dashboard
Redis 监控redis-cli info、RedisInsight看连接、命中率、内存
慢查询pg_stat_statements + pgBadger离线分析 PG 日志

八、最小可行清单​

接到"明天要压测"的需求时，至少先做完这五件事：

  1. 把 SQLAlchemy pool 事件挂上，暴露 /internal/metrics/db
  2. PG 装 pg_stat_statements 扩展，准备压测后导 top 20 慢 SQL
  3. 准备 k6 脚本：选两个最有代表性的场景（一个 read、一个长链路），各跑 baseline / ramp / soak 三种形态
  4. 压测期间每分钟采样一次 pg_stat_activity 的 state 分布
  5. 把 SLO 表先写下来贴在显眼处，压测结果直接对比，不要"看起来还行"式评估
