# 压测术语速查

> 配套词典. 用于快速回忆 baseline / ramp / soak / SLO / TTFT / 影子流量 这些词的含义和典型用法.
> 体系化讲解见 [`并发性能：观测、评估、优化`](./并发性能-观测评估与优化.md), 本篇专注名词解释 + 一行例子.

---

## 一、压测形态 (Load Test Patterns)

每种形态对应一种"我想回答什么问题". 横轴是时间, 纵轴是并发用户数 (VU = Virtual User).

```
VU
 ▲
 │ baseline (探最小延迟)              ramp (找拐点)             soak (抓泄漏)             spike (看降级)
 │  ┌──────┐                           ┌──────┐                ┌────────────────┐               ┌────────┐
50 ┤  │      │                           │      │                │                │               │        │
   │  │      │              ┌────────────┘      └────┐           │   20 VU        │   ┌───────────┘        │
 1 ┤  │      │              │                        │           │   30 分钟      │   │                    │
 0 ┼──┴──────┴──────────────┴────────────────────────┴───────────┴────────────────┴───┴────────────────────┴──► time
```

### Baseline (基线)
- **形状**: 1 VU 恒定跑短时长 (~1 分钟).
- **目的**: 探"理论最小延迟". 后续所有数字的参照物.
- **典型用法**: 新接口上线先跑 baseline 锚一下, 再做其他形态.

### Ramp / Ramp-up (阶梯爬坡)
- **形状**: 并发数阶梯式上升 (0 → 10 → 50 → 100), 总时长几分钟.
- **目的**: 找**性能拐点** —— 多少并发开始 P95 飙升.
- **关心指标**: 延迟曲线在哪个并发数开始抬头.
- **不擅长**: 抓泄漏 (太短, 慢性病浮现不出来).

### Soak / Endurance (浸泡 / 耐久)
- **形状**: 中等并发 (~20 VU) 恒定跑很久 (30 分钟 ~ 数小时).
- **目的**: 抓**慢性资源泄漏** —— 连接泄漏 / 内存泄漏 / 文件句柄泄漏.
- **关心指标**: 错误率 / 连接数 / 内存占用 是否随时间**单调上升**.
- **不擅长**: 找容量上限 (并发恒定, 不探边界).

### Spike (尖刺)
- **形状**: 几秒内瞬间拉到 100+ VU, 维持短时间后归零.
- **目的**: 看突发流量下系统是否**优雅降级** —— 限流 / 熔断 / 排队是否生效, 还是直接 5xx 雪崩.
- **典型场景**: 大促秒杀、热点新闻链接.

### Stress (压垮)
- **形状**: 并发数持续递增直到系统崩溃.
- **目的**: 找**极限承载量** + 观察崩溃方式 (优雅 vs 雪崩).
- **风险**: 真的会把目标压挂, 只能在隔离环境跑.

### Breakpoint (断点)
- **形状**: 类似 stress, 但在 SLO 第一次被违反时停止.
- **目的**: 找"在 SLA 约束下能扛多少并发", 比 stress 实用.

## 二、服务等级 (Service Level)

### SLI (Service Level Indicator, 服务等级**指标**)
- **是什么**: 一个**测出来的数**, 描述"现在系统多好".
- **例子**: 登录接口过去 5 分钟 P95 延迟 = 327ms; 过去 30 天错误率 = 0.03%.

### SLO (Service Level Objective, 服务等级**目标**)
- **是什么**: 一个**承诺的数**, 团队内部对自己定的下限.
- **形式**: "30 天内, 登录 P95 < 300ms 的请求占比 ≥ 99%".
- **作用**: 压测前定 SLO, 数字才有判断标准. 没定 SLO 的压测是"数字游戏".

### SLA (Service Level Agreement, 服务等级**协议**)
- **是什么**: 和**客户**签的合同 + 违约赔偿条款.
- **关系**: SLA 通常比内部 SLO 宽松一点, 留缓冲带.
- **例子**: "可用性低于 99.9% 退 10% 月费".

### 错误预算 (Error Budget)
- **是什么**: 1 - SLO 得到的"允许不达标量". 99.9% SLO → 每月可宕 43.2 分钟.
- **用法**: **预算用尽 → 冻结非紧急发版, 专注稳定性**. 这是 SLO 的灵魂条款, 没有这条 SLO 就只是看板.

### Status Page (状态页)
- **是什么**: SLI 的对外可视化网页 (典型: `status.openai.com`).
- **关系**: 不是 SLO 本身. 状态页展示 SLI 实测 + 当前事故, 背后的目标线才是 SLO.
- **何时该做**: 有付费客户、签了 SLA 才有必要, 初创团队不要先做 status page.

## 三、延迟指标

### P50 / P95 / P99 (分位数延迟)
- **P50** = 中位数. 一半请求比这快, 另一半比这慢.
- **P95** = 5% 的请求比这慢. **大多数 SLO 选 P95 作为承诺指标**.
- **P99** = 1% 的请求比这慢. 反映长尾, 大用户量场景下 1% 也是百万级体验.
- **不要看 avg (平均值)**: 平均会被异常值带偏, 一个 10s 的慢请求拉高几千个 100ms 请求的平均.

### TTFT (Time To First Token)
- **是什么**: LLM / SSE 流式接口的"请求 → 第一个 token 返回"的延迟.
- **为什么单独看**: 用户感知"开始响应"的是 TTFT, 不是总时长. P95 = 30s 的对话, 如果 TTFT = 300ms 用户觉得快; TTFT = 5s 用户已经走了.

### 长尾 (Long Tail)
- **是什么**: P95 和 P99 之间的差距大, 说明少部分请求异常慢.
- **常见原因**: GC pause / DB 锁等待 / 缓存击穿 / 外部依赖偶发慢.
- **诊断**: P99 / P95 比值 > 3 通常意味着有长尾问题.

### 抖动 (Jitter)
- **是什么**: 同样请求延迟波动很大 (min vs max 差几十倍).
- **常见原因**: 资源争抢 / NUMA / GC / 网络抖动.

## 四、压测环境分层 (Test Environment Tiers)

按"接近生产程度"从低到高:

### Local (本地)
- **用途**: 验证脚本能跑通 + 抓代码层 bug (连接泄漏、N+1、死锁).
- **不要做的事**: 拿本地数字推断生产容量. 网络/数据规模/规格差异巨大.

### Staging (预发环境)
- **用途**: 中小团队真正出数据的层. 与生产同部署方式, 配置常常缩水到 1/4 ~ 1/2.
- **关键要求**: 数据从生产**克隆 + 脱敏**, 否则空表压测得到的 query plan 是错的.

### Performance Environment (专设性能环境)
- **用途**: 大公司大版本前启动几天的临时环境. 与生产**完全同规格**, 成本高.
- **例子**: 阿里双十一全链路压测环境.

### Production 观察 (不直接压)
生产环境**永远不主动压**, 但有几种间接做法:

| 技术 | 含义 |
|---|---|
| **Shadow Traffic (影子流量)** | 把生产真实请求**复制**一份到 staging 异步重放, 工具如 GoReplay |
| **Canary (金丝雀)** | 新版本只给 1-5% 流量, 错误率超标自动回滚 |
| **Dark Launch (暗发布)** | 后端真实跑, 前端 UI 不暴露, 用真实流量验证后端 |
| **Feature Flag Rollout** | 用开关精细控制谁能用新功能, LaunchDarkly / Unleash |
| **Production Load Test (LTOP)** | 真在生产压, 但避开高峰 + 完整熔断兜底, **风险极高** |
| **Chaos Engineering** | 不压, 而是注入故障 (杀进程/断网络) 看系统弹性, Netflix Chaos Monkey |

## 五、k6 相关

### VU (Virtual User, 虚拟用户)
- k6 的并发单位. 1 VU = 1 个虚拟用户串行发请求.
- **VU ≠ RPS**: 1 VU 每秒能发几个请求, 取决于单请求耗时 + sleep.

### Iteration (迭代)
- k6 脚本的 `default function` 跑一遍叫一次 iteration. 通常对应"一次用户操作".

### Threshold (阈值)
- 写在 `options.thresholds` 里, **把 SLO 写进代码**.
- 未达标时 k6 进程 exit code != 0, 可以直接接 CI 当性能回归门禁.

### Scenario (场景)
- 定义"用什么 executor + 多少 VU + 多长时间"的一组配置.
- 同一个脚本可以挂多个 scenario, 通过环境变量切换.

### Executor (执行器)
- k6 内置的几种并发模型:
  - `constant-vus`: 恒定 VU (baseline / soak 用)
  - `ramping-vus`: 阶梯爬坡 (ramp / spike 用)
  - `constant-arrival-rate`: 恒定 RPS (而不是恒定 VU)
  - `ramping-arrival-rate`: 阶梯 RPS

## 六、连接池相关 (PG / SQLAlchemy)

### pool_size
- 池里**长期保持**的连接数. 类比"常驻员工数".

### max_overflow
- 突发时**临时**多开的连接上限. 类比"加班工".
- 总连接 = pool_size + max_overflow.

### pool_timeout
- 当池满时, 新请求**最多等多少秒**才超时. SQLAlchemy 默认 30s.
- **症状**: 池耗尽不会立即报错, 表现为延迟飙升 (请求在排队).

### pool_recycle
- 连接活多久就强制重建. 防 PG 端主动 kill 长闲连接造成的 stale connection.

### pool_pre_ping
- 借出连接前先 `SELECT 1` 验证还活着. 多花一次 RTT 换稳定性.

### idle in transaction
- PG 端的状态: 事务开了但没 commit/rollback 也没在执行 SQL.
- **应该接近 0**. 长期非零通常意味着应用层有事务没关 (= 连接泄漏).

## 七、关键约定 (容易踩坑)

| 约定 | 反面教材 |
|---|---|
| **ramp 必须配 PG 监控** | 只看 k6 数字, 池满和真实负载都表现为"延迟飙升", 区分不开 |
| **SLO 必须写进 threshold** | 压测脚本里手动判断"看起来还行" |
| **P95 同时看 P99** | 只看 P95, 忽略 P99 长尾, 漏 1% 的卡顿用户 |
| **TTFT 单独看** | 把流式接口和普通接口用一个 P95 指标 |
| **bcrypt 是登录的延迟天花板** | 拿登录 P95 数字推断"FastAPI 极限性能" |
| **本地数字 ≠ 生产数字** | 本地压完看 P95=50ms, 期待生产也是 50ms |
| **soak 单独跑** | 短压测 5 分钟没问题就上线, 错过了慢性泄漏 |
| **数据规模决定 query plan** | 空表压 10000 RPS 全 memory cache, 上线被百万行 seq scan 教做人 |
