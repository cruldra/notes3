SLI / SLO / SLA：服务等级目标

这套术语来自 Google SRE。三个词常被混用，但它们解决的问题完全不同：SLI 是测量、SLO 是承诺、SLA 是合同。搞清边界，才能让性能数字真正驱动工程决策。

一、三者的差别​

术语全称是什么谁定例子
SLIService Level Indicator你测量的指标工程团队"登录接口 P95 延迟"
SLOService Level Objective你承诺的目标值工程 + 产品"P95 < 300ms，30 天内 99% 时间满足"
SLAService Level Agreement你和客户的合同 + 违约赔偿法务 + 商务"可用性低于 99.9% 退月费 10%"

记忆口诀：

  • SLI = Indicator（指针）——温度计上的数字
  • SLO = Objective（目标）——"我希望温度保持在 22°C"
  • SLA = Agreement（合同）——"超过 25°C 退你钱"

SLO 严于 SLA。 内部目标 99.9%，对外合同 99.5%，中间 0.4% 是给自己的安全垫。客户感受到的是 SLA 触发，工程团队感受到的是 SLO 警报——警报先响，团队有时间在违约前止损。

二、为什么需要 SLO​

2.1 没有 SLO 的世界​

工程团队会陷入两种困境：

  • 永远不够快：每次优化都被问"还能不能更快"，没有"够好"的标准。
  • 永远不够稳：每次故障都被追问"为什么没有 100% 可用"，但 100% 既不现实也不经济。

SLO 把"够好"变成数字。达标了就去做新功能，没达标就停下来还技术债。

2.2 错误预算​

SLO 的另一面叫错误预算（Error Budget）：

错误预算 = 1 − SLO

可用性 SLO = 99.9% 意味着每月有 43 分钟的"允许失败时间"。这 43 分钟可以花在：

  • 发布新版本（每次发布都有引入故障的风险）
  • 做压力测试 / 故障演练
  • 做基础设施升级

错误预算花完了，就停止一切非必要的变更。 这是 SRE 文化的核心：开发想求快，运维想求稳，错误预算把两者的博弈变成数学题。

2.3 SLO 决定优先级​

SLO 让"该不该优化"有客观答案：

现状决策
P95 = 200ms，SLO = 300ms不优化。把时间花在 SLO 不达标的接口上。
P95 = 350ms，SLO = 300ms停下手头功能开发，优化这个接口。
P95 = 1000ms，但用户没投诉SLO 定得不对。重新审视 SLO 而不是优化代码。

最后一条最容易被忽视。SLO 应该反映用户实际感受，不是工程师的洁癖。

三、SLI 怎么选​

3.1 四个黄金信号（Google SRE）​

任何在线服务都应该至少观测这四类 SLI：

信号衡量什么典型指标
Latency（延迟）请求处理时长P50 / P95 / P99 延迟
Traffic（流量）服务被使用的强度RPS、QPS、并发连接数
Errors（错误率）失败请求占比5xx 比例、超时比例、业务失败比例
Saturation（饱和度）资源接近上限的程度CPU 使用率、DB 池占用率、队列深度

3.2 RED 方法（适合请求/响应型服务）​

  • Rate：每秒请求数
  • Errors：每秒错误数
  • Duration：请求时长分布

3.3 USE 方法（适合资源型组件，如 DB、队列、机器）​

  • Utilization：资源使用率
  • Saturation：等待队列长度
  • Errors：错误事件数

三套方法不冲突。 RED 看"服务给用户的体验"，USE 看"组件自身的健康"，黄金信号是两者的并集。

3.4 SLI 选择原则​

  • **从用户视角选，不是从代码视角选。**用户感受到的是"页面加载时间"，不是"get_user() 函数耗时"。
  • 用比率而非绝对值。"5xx 比例 < 0.1%" 比 "5xx 次数 < 100" 更有意义——后者随流量变化没意义。
  • **用分位数而非平均值。**平均延迟会被异常值掩盖。P99 才能反映尾部用户体验。

四、SLO 怎么定​

4.1 定义模板​

一条完整的 SLO 包含五要素：

【时间窗口】内，【指标】的【聚合方式】不超过【阈值】的请求占比 ≥ 【目标百分比】

例子：

30 天内，登录接口响应时长 P95 不超过 300ms 的请求占比 ≥ 99%

4.2 按场景分桶，不要混着平均​

错误示范：

"所有接口平均响应时长 < 500ms"

为什么不行：

  • 登录接口本应 < 100ms，被慢接口拉到 500ms 才达标——掩盖了真实问题
  • 长链路接口本就需要 3s，按 500ms 卡——永远不达标，团队失去信任

正确做法是按"业务路径 + 资源画像"分桶：

场景P95 SLO（参考）错误率 SLO
鉴权 / token 刷新< 300ms< 0.1%
列表 / 详情读< 500ms< 0.1%
写事务< 1s< 0.1%
长链路任务（LLM / 沙箱 / 大文件）首响应 < 3s< 1%
异步任务（Celery）入队到完成 P95 < 30s< 1%

4.3 用户感知优先​

场景用户感知阈值
点击响应100ms（感觉即时）
页面加载1s（感觉流畅）
表单提交3s（开始焦虑）
长任务首响应3s（再长就觉得卡死）

SLO 阈值贴齐这些感知边界，比凭工程师直觉拍数字更可信。

4.4 可用性怎么定​

可用性 SLO = "成功请求 / 总请求 ≥ X%"。常见档位：

SLO月允许故障适用场景
99%7.2 小时内部工具、测试环境
99.5%3.6 小时普通 SaaS（起步）
99.9%43 分钟商业 SaaS（成熟）
99.95%21 分钟金融、医疗
99.99%4.3 分钟通信、支付核心
99.999%26 秒电信级

多加一个 9，成本通常翻倍。 99.9% 到 99.99% 不是"再努力一点"，是要换架构（多活、容灾、自动故障转移）。

不要为了好看追求高位 9。客户感受不到 99.95% 和 99.99% 的差别，但工程团队感受得到。

五、错误预算怎么用​

5.1 预算消耗速度​

错误预算的关键不是"还剩多少"，是"消耗速度"。Google SRE 提出Burn Rate：

Burn Rate = 实际错误率 / SLO 允许错误率
Burn Rate含义行动
< 1比 SLO 慢健康
1–2略超关注，月底可能爆
2–10显著超立即排查
> 10严重超P1 警报、回滚最近变更

**警报应该基于 Burn Rate，不是单次故障。**单次 5xx 飙高 1 分钟不一定要叫人，但 1 小时内吃掉本月一半预算必须有人响应。

5.2 多窗口告警​

只看短窗口（5 分钟）噪音大，只看长窗口（30 天）反应慢。组合用：

窗口Burn Rate 阈值等级
5 分钟 + 1 小时> 14P1（电话/呼叫）
30 分钟 + 6 小时> 6P2（IM 警报）
6 小时 + 3 天> 1P3（工单跟进）

两个窗口同时超阈值才告警，避免单一时间窗的瞬时尖刺。

5.3 预算耗尽时的政策​

错误预算的真正价值在"耗尽时怎么办"。提前约定好规则：

  • 预算 < 0：冻结所有非必要发布；只允许修复类变更
  • 预算 < 20%：发布前必须做完整回归测试
  • 预算 > 50%：可以做更激进的实验（混沌测试、金丝雀发布扩大）

这套政策让 SLO 从"工程指标"升级为"组织契约"。

六、SLO 实践流程​

6.1 落地步骤​

  1. 选 SLI：四黄金信号 + RED 起步，每个核心接口选 2–3 个
  2. 定 SLO：用历史 30 天数据看 P95 / P99 实际值，目标定在比实际严 10–20%
  3. 接监控：Prometheus 抓 metric，Grafana 出 dashboard，告警基于 Burn Rate
  4. 写 Runbook：SLO 违约时谁响应、怎么排查、怎么止损
  5. 月度复盘：哪些 SLO 持续达标可以收紧、哪些屡次不达标要么改架构要么调 SLO

6.2 反模式​

想法反驳
"SLO 越严越好"SLO 太严，警报噪音淹没团队，反而无人响应。
"100% 可用最理想"100% 既不可达也不经济。永远会有网络、电力、人为故障。
"用平均延迟当 SLO"平均被异常值掩盖，1% 的用户卡 10 秒看不出来。
"SLO 一年定一次"SLO 是活的。基础设施改了、用户量涨了，都要调。
"SLO 是技术指标，不用让产品看"SLO 直接影响"该做新功能还是还债"的决策，产品必须在场。
"达标率 99% 意味着 1% 用户体验差就行"错。1% 的 5xx 可能集中在同一批关键用户身上。
"我们只关心可用性，不定延迟 SLO"慢 = 不可用。3 秒返回还是 30 秒返回，对用户是质的差别。

6.3 SLO 不适合做什么​

  • 不适合衡量代码质量：SLO 是用户体感，圈复杂度、测试覆盖率才是质量
  • 不适合考核个人：把 SLO 和绩效挂钩会扭曲行为（团队会偷偷调 SLO 阈值）
  • 不适合替代故障复盘：SLO 告诉你"哪里坏了"，复盘告诉你"为什么坏"

七、一个完整例子​

假设有一个多用户 SaaS 后端，三个核心接口：

7.1 SLI 清单​

SLI测量方式来源
登录接口 P95 延迟http_request_duration_seconds{route="/auth/login"}Prometheus
会话列表 5xx 比例rate(http_requests_total{route="/sessions",status=~"5.."}[5m])Prometheus
长链路任务首响应时间自打点 trace spanOpenTelemetry
Celery 任务延迟 P95celery_task_runtime_secondscelery-exporter

7.2 SLO 表​

接口SLISLO错误预算（月）
/auth/loginP95 延迟30 天 99% < 300ms7.2 小时不达标
/sessions5xx 比例30 天 99.9% 成功43 分钟
/agent/invoke首响应 P9530 天 95% < 3s36 小时不达标
Celery 任务延迟 P9530 天 99% < 30s7.2 小时不达标

7.3 告警​

告警条件等级
登录快速燃尽5min 和 1h Burn Rate 都 > 14P1，叫人
会话 5xx 中速燃尽30min 和 6h Burn Rate 都 > 6P2，IM
长链路慢速燃尽6h 和 3d Burn Rate 都 > 1P3，工单

7.4 月度复盘​

  • 登录 SLO 连续 3 月达标率 100%，可以收紧到 P95 < 200ms
  • 长链路 SLO 多次不达标，但用户没投诉——SLO 定得太严，放宽到 < 5s
  • Celery SLO 屡次违约，根因是任务积压——改架构（分队列、加 worker）
